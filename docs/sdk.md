# FerroUI phone application SDK

The phone now composes independently compiled Rust applications through `phone-sdk`. The system shell and the apps share retained FerroUI controls, the phone theme and host services. Built-in apps use the same registration and lifecycle boundary as additional applications.

This is a trusted, statically linked Rust SDK. It does not load XAP/APPX packages, implement the original Windows Runtime ABI, sandbox native Rust code or connect retired Microsoft services. The target remains the Windows Phone 8.1 Update user experience; the SDK provides an extensible implementation architecture for that recreation.

## Dependency direction

`phone-sdk` depends on the shared domain, reactive state, host contracts, controls and FerroUI primitives. It does not depend on `phone-system` or on application crates. `phone-system` renders Start, the app list, navigation, lock screen, Action Center, hardware panels and foreground alert surfaces. It selects applications through an immutable `AppRegistry`.

`phone-ui` is the composition facade used by browser and desktop hosts. It supplies the built-in registrations and preserves the host-facing API. Application source is under `crates/apps`, outside the system shell. The separate `phone-alarm-service` contains foreground alarm scheduling and editor state shared by the Alarms app and system alert surface.

| Layer | Responsibility |
| --- | --- |
| `phone-domain` | Serializable models, validation, routes, portable document/PIM codecs and bounded app data namespaces. |
| `phone-state` | ReactiveUI view model, commands, DynamicData projections, persistence and navigation journal. |
| `phone-host` | Portable host requests/observations and reusable native primitives. |
| `phone-controls` | Phone control templates, typography, palette, icons and animation primitives. |
| `phone-sdk` | App manifests, registry contracts, contexts, typed session state, persistent app storage, shared page helpers and host surface slots. |
| `phone-system` | System UI, gesture arbitration and lifecycle dispatch. |
| `phone-ui` | Built-in composition and compatible host facade. |
| `phone-app-*` | An app's view, app-specific transient state, registration and interaction handlers. |

The shell contains no app-specific dispatch switch. Registrations identify built-in route owners or additional application IDs. The existing document, contact, conversation and folder routes retain their serialized form; added apps use `Route::Extension { app, path }`.

## Create an app

The scaffolder creates a complete workspace crate with its manifest, `build.rs`, declarative view and a versioned persistent counter example:

```bash
python scripts/new-phone-app.py phone-app-counter \
  --title Counter --id example.counter --dry-run

python scripts/new-phone-app.py phone-app-counter \
  --title Counter --id example.counter
```

`--dry-run` writes nothing. The script refuses existing output paths, validates the Cargo name and app ID, and reserves `phone.*` for built-in identities. `--output` selects another new directory. Generated manifests inherit the phone workspace's pinned FerroUI dependencies; place the generated crate inside this workspace before building it.

The script intentionally leaves composition explicit. Add the generated crate as a dependency of the composing host/facade, then add its `registration()` to the vector passed to `phone_ui::create_view_with_apps`. The default `phone_ui::create_view` uses the supplied built-in composition. No dynamic library loader or online installation channel is involved.

```rust
let view = phone_ui::create_view_with_apps(
    vm,
    vec![phone_app_counter::registration()],
)?;
```

`create_view_with_apps` adds these registrations to the built-in composition. For a replacement composition, construct `AppRegistry::new(custom_apps)?` and pass it in an `Rc` directly to `phone_system::create_view`. `phone_ui::built_in_apps()` exposes the standard registrations when a host needs to inspect or adapt that vector before building its registry.

The checked-in `crates/apps/phone-app-sdk-example` package is generated by this script and can be built with `cargo check -p phone-app-sdk-example`. It is intentionally absent from the default phone composition; pass its registration to `create_view_with_apps` to include the counter in your own build. Use this package as a concrete template when developing a new app.

A new app does not require changing the system shell or adding an `AppId` enum variant. A stable application ID is also its persistent storage namespace; changing that identity creates a different namespace.

## Registration and declarative views

A minimal registration consists of a manifest and a renderer accepting `AppContext`:

```rust
use phone_sdk::prelude::*;

pub fn registration() -> AppRegistration {
    AppRegistration::new(
        AppManifest::new("example.hello", "Hello", Icon::Note)
            .category(AppCategory::Utility),
        |cx| {
            let close = cx.vm.clone();
            page(
                "hello",
                scroll(rsx! {
                    StackPanel { margin:20.0, spacing:16.0,
                        {title("hello")}
                        {text("A retained FerroUI application.", 24.0)}
                        {flat("start", move || close.home())}
                    }
                }),
                Element::Empty,
            )
        },
    )
}
```

`AppManifest` carries the stable ID, title, version, icon, accent, category, listed state and declared capabilities. Its `route(path)` produces a built-in app route or an extension route as appropriate. `AppRegistry::new` validates identities and rejects duplicate application IDs and duplicate built-in ownership; registration order cannot silently replace another application.

The SDK prelude exposes the same `rsx!` API and reusable phone primitives used by the built-ins. Native control templates, accessibility names, keyboard behavior and retained reconciliation remain FerroUI responsibilities. Do not implement a second HTML UI for an app hosted by the browser edition.

## Transient app state

Each app defines its own state type and requests the shared instance through `Session::state::<T>()`:

```rust
use phone_sdk::prelude::*;

struct EditorSession {
    draft: Signal<String>,
    searching: Signal<bool>,
}
impl Default for EditorSession {
    fn default() -> Self {
        Self { draft: signal(String::new()), searching: signal(false) }
    }
}

fn editor(cx: AppContext) -> Element {
    let state = cx.session.state::<EditorSession>();
    rsx! { TextBox {
        class:"phone-input",
        automation_properties_name:"Draft",
        text:state.draft.two_way(),
    }}
}
```

The store is typed by `TypeId` and returns an `Rc<T>`. Use an app-private state type; two apps deliberately using the same type share that state. A stable session owner owns the state's reactive signals, so re-rendering or detaching a page does not dispose the app's draft signals. App state should contain UI-thread data, not cross-thread native resources.

Phone dialing, Calculator, Photos zoom, Outlook selection/folder state, Messaging drafts, browser navigation UI, Calendar editing, Files selections and Office editor state now live in their owning app or a reusable support crate. The SDK does not import those types. Common page commands, dialogs and the system media transport remain shared session facilities.

Use lifecycle/reset hooks to release transient resources and clear state when a different phone document replaces the current one. Preserve unsaved drafts when the system merely covers an app with its in-app lock screen.

## Persistent app data

`AppContext::storage()` returns an `AppStorage` bound to the registration's ID. Its `read<T>()`, `write(&T)` and `clear()` methods use the phone's existing persistent document and backup transaction.

```rust
#[derive(serde::Serialize, serde::Deserialize)]
struct Preferences {
    schema: u32,
    sound: bool,
}
impl Default for Preferences {
    fn default() -> Self { Self { schema: 1, sound: true } }
}

let storage = cx.storage();
let mut preferences = storage.read::<Preferences>()?;
if preferences.schema != 1 {
    return Err("Unsupported preferences version.".into());
}
preferences.sound = false;
storage.write(&preferences)?;
```

The phone supports at most 256 app namespaces and 256 KiB of serialized JSON per namespace, subject to the complete phone-document limit. JSON values are limited to 32 nested levels and 16,384 nodes. Integer values must lie within JavaScript's exact range, −9,007,199,254,740,991 through 9,007,199,254,740,991, so browser backup transport cannot silently round them; encode larger identifiers as strings. Writes and restored backups use the same validation. Rejected writes leave the old namespace intact. Each app owns schema versions and migrations. Invalid or unsupported stored data must be reported or migrated explicitly; do not overwrite it with defaults after a decode error. Small committed changes belong in app storage; image/audio/video bytes belong in host asset storage.

Application data survives a normal reload and participates in phone backup/restore. This is logical namespacing within one trusted document, not encryption or isolation from other linked Rust code. The general persistence callback and host save-error reporting retain their existing semantics; a successful UI command does not certify physical storage durability on every host.

## Lifecycle and input hooks

| Registration hook | Use |
| --- | --- |
| `with_back` | Consume Back for an app-owned transient view before the system pops navigation. Return `false` when the shell should continue. |
| `with_backspace_input` | Keep unmodified Backspace for an app-owned input surface such as Calculator. Hardware Back and Escape retain system behavior; native TextBox editing is protected automatically. |
| `with_route_changed` | Observe previous/next routes and reset appropriate page state. Internal detail navigation and leaving an app can require different treatment. |
| `with_deactivate` | Close app-owned transient UI when the system clears the active app's overlays. |
| `with_reset` | Clear transient state when phone data is replaced or its data is explicitly reset. Persistent app data comes from the current document. |
| `with_lifecycle` | Handle `Activated`, `Deactivated`, `Suspended`, `Resumed`, `Closing` and `Reset` events dispatched by the system/host. |
| `with_pivot_count` | Declare available cyclic pivot sections for system gesture arbitration. Return zero for pages that should keep horizontal input. |
| `with_can_swipe` / `with_swipe` | Provide app-specific horizontal navigation, such as Calendar periods or photo stepping. |
| `with_overlay` | Identify app-owned overlays that should block host surfaces or preview capture. |
| `with_activation` | Accept validated JSON after destination navigation and lifecycle reset. Return a descriptive error for an unsupported payload. |
| `with_tile` | Render a retained tile surface from the registered app context, saved launch path, size and system cadence. |
| `with_tick` | Receive foreground clock ticks for the active app. Keep work bounded; no background wake-up guarantee follows from this hook. |
| `with_host_navigation` | Receive the browser host's acknowledgement of app-requested navigation. |
| `with_host_weather` | Receive a host weather result. This is observed external data, not generated weather. |

A callback must not retain a borrowed view-model document across a mutation, await point or host callback. Snapshot IDs/values, release the borrow, then dispatch. Use stable automation names on important controls so rendered tests can drive actual input.

## App discovery, Start tiles and recent apps

Registered, listed apps appear in All apps and in Store without modifying an `AppId` enum or adding a shell match arm. The Games hub selects registrations whose category is `AppCategory::Game`. Disabled extensions stay in Store so they can be enabled again; they are omitted from All apps and Games and cannot be navigated to. Removing a registration makes its routes unavailable without deleting its stored namespace.

Store uses the included app registry; it is not a network package marketplace. Enabling an extension makes already linked code available. Disabling an extension removes its Start launch links and recent/back entries while preserving saved app data. Resetting that namespace is a separate, confirmed action. The shell delivers `Closing` when an app is closed from recents or disabled, and `Reset` after an explicit app-data reset. Closing does not implicitly invoke reset hooks or discard unsaved app drafts; an app can handle `Closing` if it needs to release resources or persist/clear its own transient state. Pending SDK file tasks are cancelled on close, reset and session replacement.

The recent-app journal interleaves built-ins and extensions, resumes an extension's last valid path and drops that path on close. Built-in cards use captured previews where available. Extension cards currently use their registered icon/title/accent; they do not claim to contain a captured application screenshot.

An app can pin its root or a document-specific path:

```rust
cx.pin("documents/42", "Project plan")?;
```

This validates the registered, enabled identity, path (up to 2,048 bytes, no control characters), printable title and Start capacity before atomically allocating the launch-link and tile records. Repeating the same app/path is idempotent. Launch links survive folder moves, resizing, phone reload and backup/restore. The canonical record is `PhoneData.app_links`; `TileTarget::AppLink(id)` references it. The legacy `Tile.app` enum is only a compatibility fallback for these tiles and must not be used to select their registration. New code resolves the link's app identity through the registry.

By default, extension tiles use the manifest icon/accent and saved label. `.with_tile(render)` supplies custom content:

```rust
fn render_tile(cx: phone_sdk::AppTileContext) -> phone_sdk::prelude::Element {
    use phone_sdk::prelude::*;
    let path = cx.path;
    rsx! { StackPanel { margin:12.0, spacing:8.0,
        {text("project", 24.0)}
        {muted(&path, 14.0)}
    }}
}
```

`AppTileContext` includes `app`, `size`, `width`, `height`, `path`, `now`, `live` and `animate`. Respect `animate` before adding motion, and treat `now == 0` with `live == false` as a paused cadence. The shell supplies the label and the bounded tile container. Keep rendering side-effect free; use namespaced data or typed app state and the supplied cadence for live content. The system stops cadence updates when live tiles are disabled or obscured, and tile rendering does not itself create background execution. Weather's live tile is implemented through this same callback in the Weather app crate.

## Data activation

Use an app's route for normal navigation. For a structured activation, queue one JSON payload, then navigate to its destination. Delivery occurs after route lifecycle callbacks reset the destination UI:

```rust
let destination = cx.session.registry().by_id("phone.calendar")
    .ok_or("Calendar is unavailable")?.manifest.route("");
cx.session.queue_activation("phone.calendar", serde_json::to_value(occurrence)?)?;
cx.vm.navigate(destination);
```

The session keeps one pending activation, bounded to 64 KiB. Delivery uses `AppRegistry::activate`, which rejects unknown, disabled and inactive destinations and validates the JSON value. The destination owns payload decoding through `.with_activation`. Calendar reminders use this contract to open an exact occurrence without making the system or alarm service depend on the Calendar app crate. An activation is an in-process SDK message, not an implementation of Windows Phone URI-association or XAP activation compatibility.

## Host capabilities and surfaces

Use `AppContext::request` to request host services. It checks that the app remains installed/enabled and verifies the requested service family against the manifest's declared capabilities before forwarding to the existing host adapter. Declare only the families used by the app. The browser or native OS still owns its permissions, prompts and delivery outcome.

```rust
let manifest = AppManifest::new("example.camera", "Camera tool", Icon::Camera)
    .capabilities(&[Capability::Camera]);
// Inside the registered app's event handler:
cx.request(phone_sdk::host::HostRequest::StartCamera)?;
```

### Typed file selection

`AppContext::choose_file(FilePickerOptions)` returns a `FileTask` future with `Result<Option<PickedFile>, String>`. Cancellation by the user returns `Ok(None)`; a selected file includes its display name, MIME type and byte vector. The manifest must declare `Capability::Files`. Options restrict extensions and a maximum byte count; the SDK validates host results again before completing the future.

Create the task synchronously inside the user event, before scheduling the async block, so browser file selection retains the original user activation:

```rust
let selection = cx.choose_file(phone_sdk::FilePickerOptions {
    extensions: vec![".txt".into(), ".md".into()],
    max_bytes: 256 * 1024,
});
let epoch = cx.vm.document_epoch();
let vm = cx.vm.clone();
drop(ferroui_base::threading::Dispatcher::current_dispatcher().spawn_local(async move {
    let result = selection.await;
    if vm.document_epoch() != epoch { return; }
    match result {
        Ok(Some(file)) => { /* Validate the content, then apply app-owned changes. */ }
        Ok(None) => {}
        Err(error) => vm.set_status(error),
    }
}));
```

The task is cancelled when its future is dropped, the app closes or resets, or the session ends. Stale completions after a phone restore cannot mutate the replacement document. OneNote's text/Markdown import is an end-to-end consumer of this API and rejects non-UTF-8/binary content before creating a note. The chooser is for one bounded file, not arbitrary filesystem access.

Capabilities are an application contract for trusted code. `AppContext` exposes the existing view model, and statically linked Rust can access other public APIs; declarations are not a security sandbox. File selection, sharing, notification permission and location acquisition should remain explicit user actions. Do not request permissions just to populate a Settings page.

Camera and video app views place `host_surface(HostSurface::Camera)` or `host_surface(HostSurface::Video)` in their retained preview containers. A native host can install a control factory with `set_host_surface_factory`. An unavailable surface produces an empty element, preserving the normal view and browser overlay geometry. Host adapters own their native device/player lifecycle; the app owns layout and commands.

For the browser host, name the surrounding retained container `CameraViewport` or `MediaViewport` respectively, give it a background so the native inspection hit test identifies its bounds, and keep it inside the app's normal content area. The browser positions its permitted media element over that control. The built-in Camera and shared media views are concrete examples of this contract; using only `host_surface` without that container does not create a browser overlay. Host surfaces are foreground UI and do not grant background capture or playback scheduling.

Shared image helpers admit and cache application media for app lists, Photos, lock backgrounds and tiles. Use the existing host/SDK service rather than decoding arbitrary files independently in every app.

## Verification boundaries

The crate split preserves the existing native control IDs and app workflows so the rendered interaction suite can exercise the migrated implementation. Compile-time dependency checks establish the direction of reuse; Rust and JavaScript boundary tests establish selected state/host behavior; browser screenshots establish the rendered states they capture. None of those alone certifies original-device pixel parity, real OS permission dialogs, complete cloud-account services, dynamic third-party package loading or every physical platform.

See [host integration](host-integration.md), [interchange formats](pim-interchange.md), [architecture](architecture.md), and the revision-specific [verification record](parity.md) for implemented behavior and measured coverage.
