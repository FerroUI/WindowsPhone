# FerroUI phone application SDK

The phone now composes independently compiled Rust applications through `phone-sdk`. The system shell and the apps share retained FerroUI controls, the phone theme and host services. Built-in apps use the same registration and lifecycle boundary as additional applications.

This is a trusted, statically linked Rust SDK. It does not load XAP/APPX packages, implement the original Windows Runtime ABI, sandbox native Rust code or connect retired Microsoft services. The target remains the Windows Phone 8.1 Update user experience; the SDK provides an extensible implementation architecture for that recreation.

## Dependency direction

`phone-sdk` depends on the shared domain, reactive state, host contracts, controls and FerroUI primitives. It does not depend on `phone-system` or on application crates. `phone-system` renders Start, the app list, navigation, lock screen, Action Center, hardware panels and foreground alert surfaces. It selects applications through an immutable `AppRegistry`.

`phone-ui` is the composition facade used by browser and desktop hosts. It supplies the built-in registrations and preserves the host-facing API. Application source is under `crates/apps`, outside the system shell. The separate `phone-alarm-service` contains foreground alarm scheduling and editor state shared by the Alarms app and system alert surface.

| Layer | Responsibility |
| --- | --- |
| `phone-domain` | Serializable models, validation, routes, portable document/PIM codecs and bounded app data namespaces. |
| `phone-state` | ReactiveUI view model, commands, DynamicData projections, persistence and navigation journal. |
| `phone-host` | Portable host requests/observations and reusable native primitives. |
| `phone-controls` | Phone control templates, typography, palette, icons and animation primitives. |
| `phone-sdk` | App manifests, registry contracts, contexts, typed session state, persistent app storage, shared page helpers and host surface slots. |
| `phone-system` | System UI, gesture arbitration and lifecycle dispatch. |
| `phone-ui` | Built-in composition and compatible host facade. |
| `phone-app-*` | An app's view, app-specific transient state, registration and interaction handlers. |

The shell contains no app-specific dispatch switch. Registrations identify built-in route owners or additional application IDs. The existing document, contact, conversation and folder routes retain their serialized form; added apps use `Route::Extension { app, path }`.

## Create an app

The scaffolder creates a complete workspace crate with its manifest, `build.rs`, declarative view and a versioned persistent counter example:

```bash
python scripts/new-phone-app.py phone-app-counter \
  --title Counter --id example.counter --dry-run

python scripts/new-phone-app.py phone-app-counter \
  --title Counter --id example.counter
```

`--dry-run` writes nothing. The script refuses existing output paths, validates the Cargo name and app ID, and reserves `phone.*` for built-in identities. `--output` selects another new directory. The default `crates/apps/*` location is already a workspace member through the root manifest's glob. A different output location must be added to the workspace members explicitly, or to another workspace supplying the inherited package fields and dependencies, before building it; placement elsewhere inside this repository alone does not establish membership.

The script intentionally leaves composition explicit. Add the generated crate as a dependency of the composing host/facade, then add its `registration()` to the vector passed to `phone_ui::create_view_with_apps`. The default `phone_ui::create_view` uses the supplied built-in composition. No dynamic library loader or online installation channel is involved.

```rust
let view = phone_ui::create_view_with_apps(
    vm,
    vec![phone_app_counter::registration()],
)?;
```

`create_view_with_apps` adds these registrations to the built-in composition. For a replacement composition, construct `AppRegistry::new(custom_apps)?` and pass it in an `Rc` directly to `phone_system::create_view`. `phone_ui::built_in_apps()` exposes the standard registrations when a host needs to inspect or adapt that vector before building its registry.

Shell composition calls `AppRegistry::bind(&PhoneViewModel)` automatically. A standalone SDK host or test must call `registry.bind(&vm)` before issuing app commands. This binds built-in identities and extension identities separately: installed built-ins can own secondary Start links without becoming extensions or acquiring extension enable/disable routes. Do not add a built-in ID to `set_registered_apps` to bypass this distinction.

The checked-in `crates/apps/phone-app-sdk-example` package is generated by this script and can be built with `cargo check -p phone-app-sdk-example`. It is intentionally absent from the default phone composition; pass its registration to `create_view_with_apps` to include the counter in your own build. Use this package as a concrete template when developing a new app.

A new app does not require changing the system shell or adding an `AppId` enum variant. A stable application ID is also its persistent storage namespace; changing that identity creates a different namespace.

## Registration and declarative views

A minimal registration consists of a manifest and a renderer accepting `AppContext`:

```rust
use phone_sdk::prelude::*;

pub fn registration() -> AppRegistration {
    AppRegistration::new(
        AppManifest::new("example.hello", "Hello", Icon::Note)
            .category(AppCategory::Utility),
        |cx| {
            let close = cx.vm.clone();
            page(
                "hello",
                scroll(rsx! {
                    StackPanel { margin:20.0, spacing:16.0,
                        {title("hello")}
                        {text("A retained FerroUI application.", 24.0)}
                        {flat("start", move || close.home())}
                    }
                }),
                Element::Empty,
            )
        },
    )
}
```

`AppManifest` carries the stable ID, title, version, icon, accent, category, listed state and declared capabilities. Its `route(path)` produces a built-in app route or an extension route as appropriate. `AppRegistry::new` validates identities and rejects duplicate application IDs and duplicate built-in ownership; registration order cannot silently replace another application.

`AppRegistry::search_apps(vm, query)` discovers listed, installed/enabled applications by case-insensitive title substring or exact ID, with stable relevance ordering. `resolve_app` selects a unique case-insensitive ID match, a unique exact title or a unique substring match; ambiguous titles and IDs differing only by case are never silently opened. `search_local` combines the same registry catalog with existing contact, note and Office results, filtering unavailable route owners and returning at most 100 rows. Cortana uses these APIs for local results and `open` commands, so additional SDK apps need no search-specific shell changes. Disabling an app in Store removes it from local discovery immediately. Unknown or ambiguous local commands remain on the search page; only explicit web-search actions leave the phone.

The SDK prelude exposes the same `rsx!` API and reusable phone primitives used by the built-ins. Native control templates, accessibility names, keyboard behavior and retained reconciliation remain FerroUI responsibilities. Do not implement a second HTML UI for an app hosted by the browser edition.

## Transient app state

Each app defines its own state type and requests the shared instance through `Session::state::<T>()`:

```rust
use phone_sdk::prelude::*;

struct EditorSession {
    draft: Signal<String>,
    searching: Signal<bool>,
}
impl Default for EditorSession {
    fn default() -> Self {
        Self { draft: signal(String::new()), searching: signal(false) }
    }
}

fn editor(cx: AppContext) -> Element {
    let state = cx.session.state::<EditorSession>();
    rsx! { TextBox {
        class:"phone-input",
        automation_properties_name:"Draft",
        text:state.draft.two_way(),
    }}
}
```

The store is typed by `TypeId` and returns an `Rc<T>`. Use an app-private state type; two apps deliberately using the same type share that state. A stable session owner owns the state's reactive signals, so re-rendering or detaching a page does not dispose the app's draft signals. App state should contain UI-thread data, not cross-thread native resources.

Phone dialing, Calculator, Photos zoom, Outlook selection/folder/composer state, Messaging drafts, browser navigation UI, Calendar editing, Files selections and Office editor state now live in their owning app or a reusable support crate. The SDK does not import those types. Common page commands, dialogs and the system media transport remain shared session facilities.

Use lifecycle/reset hooks to release transient resources and clear state when a different phone document replaces the current one. Preserve unsaved drafts when the system merely covers an app with its in-app lock screen.

## Persistent app data

`AppContext::storage()` returns an `AppStorage` bound to the registration's ID. Its `read<T>()`, `write(&T)` and `clear()` methods use the phone's existing persistent document and backup transaction.

```rust
#[derive(serde::Serialize, serde::Deserialize)]
struct Preferences {
    schema: u32,
    sound: bool,
}
impl Default for Preferences {
    fn default() -> Self { Self { schema: 1, sound: true } }
}

let storage = cx.storage();
let mut preferences = storage.read::<Preferences>()?;
if preferences.schema != 1 {
    return Err("Unsupported preferences version.".into());
}
preferences.sound = false;
storage.write(&preferences)?;
```

The phone supports at most 256 app namespaces and 256 KiB of serialized JSON per namespace, subject to the complete phone-document limit. JSON values are limited to 32 nested levels and 16,384 nodes. Integer values must lie within JavaScript's exact range, −9,007,199,254,740,991 through 9,007,199,254,740,991, so browser backup transport cannot silently round them; encode larger identifiers as strings. Writes and restored backups use the same validation. Rejected writes leave the old namespace intact. Each app owns schema versions and migrations. Invalid or unsupported stored data must be reported or migrated explicitly; do not overwrite it with defaults after a decode error. Small committed changes belong in app storage; image/audio/video bytes belong in host asset storage.

Application data survives a normal reload and participates in phone backup/restore. This is logical namespacing within one trusted document, not encryption or isolation from other linked Rust code. The general persistence callback and host save-error reporting retain their existing semantics; a successful UI command does not certify physical storage durability on every host.

### Outlook draft example

`phone-app-outlook` keeps saved mail composition in the built-in identity's `phone.outlook` namespace. Its version-1 schema is `{version, next_id, items: [{id, fields: {to, subject, body}, updated}]}`; `updated` is a timestamp in seconds. Draft IDs remain stable on replacement. Validation bounds the collection to 100 drafts, each header to 4 KiB and body to 64 KiB, within the SDK's stricter aggregate namespace/document budgets. Unsupported or malformed stored data is reported without resetting it.

The editor keeps unsaved fields and its saved baseline in typed session state. Editing fields does not write storage. Save draft commits the editor; confirmed deletion updates the saved draft collection. Back confirms discard of changed fields; cancellation keeps the editor, while discarding changes preserves an existing saved version. Ordinary deactivation retains the editor; reset clears its transient state. Local draft navigation uses a separate flag and cannot hide an imported mail folder named `drafts`.

`HostRequest::Email` requests host composition and has no delivery acknowledgement. Opening the host email app therefore neither persists current edits, removes a saved draft, nor adds a sent-mail entry. This is a concrete example of separating a user-owned local document from an external action's observed result. Native draft contracts and rendered editor/persistence workflows have separate exact-source records; see [the verification index](verification/metro-refinement/README.md) and [remaining parity](parity.md#metro-and-outlook-refinement).

## Metro controls and pivot pages

Use the phone helpers `toggle`, `check` and `radio` for native ToggleSwitch, CheckBox and RadioButton behavior. For a directly declared native control, `checked_state` supplies an `Option<bool>` value and a render-owned change callback:

```rust
use ferroui_view::prelude::*;

fn repeat_day(enabled: bool, update: impl Fn(bool) + 'static) -> Element {
    rsx! { CheckBox {
        class:"phone-check", content:"Monday",
        automation_properties_name:"Repeat on Monday",
        is_checked:phone_controls::checked_state(
            Some(enabled), move |next| update(next.unwrap_or(false))
        ),
    } }
}
```

Model reconciliation replaces the prior subscription, initializes the retained control, then listens for native pointer/keyboard/automation changes. It must not echo a model refresh through an obsolete callback. `None` remains available for an indeterminate checkbox; radio helpers publish selection only when checked. App code should not synthesize clicks to reproduce native selection or switch dragging.

`pivot_pages` accepts a stable automation name, the app's selected-index signal and retained `PivotPage` values. Give each pane its own vertical scroller; wrapping the whole pivot in a scroller prevents it from receiving a finite page viewport.

```rust
use phone_controls::{pivot_pages, PivotPage};
use phone_sdk::{common::scroll, session::Session};

fn hub(ui: &Session, first: Element, second: Element) -> Element {
    pivot_pages("ExamplePivot", ui.pivot, vec![
        PivotPage::new("overview", scroll(first)),
        PivotPage::new("details", scroll(second)),
    ])
}
```

Declare the matching `with_pivot_count` for shell arbitration and return zero while a detail editor or picker owns horizontal input. Native panes own their manipulation; avoid a second manual swipe handler advancing the same gesture. Battery Saver, Data Sense and Games are the current integrations. The phone Pivot disables inherited item auto-scroll so native pan, snap and selection own one consistent viewport; mounted regressions cover both wrap directions and actual composed content alignment. The reduced-motion path keeps the same selection and headers without compositor animation.

`app_bar` allows four primary commands plus a separate ellipsis and moves additional commands into its text menu. SDK composition connects expansion to `Session::menu`; shared page helpers overlay the bounded menu and prevent a dismissal click from activating page content. Do not implement an independent Back/menu state in each app. Captions remain a single ellipsized line; primary commands use native pressed/disabled ink states and retain stable input bounds.

Native `DatePicker`/`TimePicker` declarations using `attach_picker_focus` receive the shared full phone presenter. Their native values remain staged until confirmation, and the shell owns Back/Home/privacy dismissal. `dismiss_phone_picker()` consumes Back (including collapse of expanded picker commands); `close_phone_pickers()` tears surfaces down immediately before navigation or privacy coverage without committing. Do not call confirmation handlers or implement a second picker journal in app code. Native range, calendar, increment, locale and keyboard behavior remain authoritative; optional seconds are a supported extension to the original three-column page.

Structural button, choice, slider and picker templates remain mounted across palette replacement, preserving selection and input state. A `TextBox.phone-input` keeps its native presenter, selection/composition and undo history while styles change its phone chrome. Read-only fields remain selectable and copyable. Desktop keyboard-focus overlays and the exact neutral state colors are adaptations documented in [the source record](metro-design.md).

Shell turnstiles and press tilt use the [documented original constants](metro-design.md). The navigation controller retains at most one noninteractive outgoing page image for its 250 ms exit and then enters the sole live destination over 350 ms. The outgoing image clears on completion, cancellation, privacy coverage, resize, unload or motion suppression; capture failure uses incoming-only motion. App lifecycle and route changes remain synchronous. Full Panorama, continuum and original-device transition comparison remain incomplete.

Use `command` for a standalone text command, or `command_button` when a native `El<Button>` must be named or placed explicitly. Its caption wraps and follows text scaling within a minimum 44-unit height. `Session::confirm` uses the explicit text `confirm`; `form` uses `save`; `form_with_action` supplies a specific action such as `discard` or `delete`. Dialogs use readable text commands and never guess a destructive action’s icon from its label. Only a collapsed `phone-app-bar` hides its descendant icon captions; unrelated actions have no ellipsis and retain their labels.

## Lifecycle and input hooks

| Registration hook | Use |
| --- | --- |
| `with_back` | Consume Back for an app-owned transient view before the system pops navigation. Return `false` when the shell should continue. |
| `with_backspace_input` | Keep unmodified Backspace for an app-owned input surface such as Calculator. Hardware Back and Escape retain system behavior; native TextBox editing is protected automatically. |
| `with_route_changed` | Observe previous/next routes and reset appropriate page state. Internal detail navigation and leaving an app can require different treatment. |
| `with_deactivate` | Close app-owned transient UI when the system clears the active app's overlays. |
| `with_reset` | Clear transient state when phone data is replaced or its data is explicitly reset. Persistent app data comes from the current document. |
| `with_lifecycle` | Handle `Activated`, `Deactivated`, `Suspended`, `Resumed`, `Closing` and `Reset` events dispatched by the system/host. |
| `with_pivot_count` | Declare available cyclic pivot sections for system gesture arbitration. Return zero for pages that should keep horizontal input. |
| `with_can_swipe` / `with_swipe` | Provide app-specific horizontal navigation, such as Calendar periods or photo stepping. |
| `with_overlay` | Identify app-owned overlays that should block host surfaces or preview capture. |
| `with_activation` | Accept validated JSON after destination navigation and lifecycle reset. Return a descriptive error for an unsupported payload. |
| `with_launch_path` | Parse a built-in app's nonempty launch path into bounded activation JSON before navigation or pinning. Pair it with `with_activation`. |
| `with_tile` | Render a retained tile surface from the registered app context, saved launch path, size and system cadence. |
| `with_tick` | Receive foreground clock ticks for the active app. Keep work bounded; no background wake-up guarantee follows from this hook. |
| `with_media_event` | Observe the current library player's source-bound progress, pause/checkpoint and completion while any app is visible. Requires an enabled registration declaring `Media` or `All`. |
| `with_host_navigation` | Receive the browser host's acknowledgement of app-requested navigation. |
| `with_host_weather` | Receive a host weather result. This is observed external data, not generated weather. |

A callback must not retain a borrowed view-model document across a mutation, await point or host callback. Snapshot IDs/values, release the borrow, then dispatch. Use stable automation names on important controls so rendered tests can drive actual input.

## App discovery, Start tiles and recent apps

Registered, listed apps appear in All apps and in Store without modifying an `AppId` enum or adding a shell match arm. The Games hub selects registrations whose category is `AppCategory::Game`. Disabled extensions stay in Store so they can be enabled again; they are omitted from All apps and Games and cannot be navigated to. Removing a registration makes its routes unavailable without deleting its stored namespace.

Store uses the included app registry; it is not a network package marketplace. Enabling an extension makes already linked code available. Disabling an extension removes its Start launch links and recent/back entries while preserving saved app data. Resetting that namespace is a separate, confirmed action. The shell delivers `Closing` when an app is closed from recents or disabled, and `Reset` after an explicit app-data reset. Closing does not implicitly invoke reset hooks or discard unsaved app drafts; an app can handle `Closing` if it needs to release resources or persist/clear its own transient state. Pending SDK file and HTTPS tasks are cancelled on close, reset and session replacement.

The recent-app journal interleaves built-ins and extensions, resumes an extension's last valid path and drops that path on close. Built-in cards use captured previews where available. Extension cards currently use their registered icon/title/accent; they do not claim to contain a captured application screenshot.

An app can pin its root or a document-specific path:

```rust
cx.pin("documents/42", "Project plan")?;
```

This validates the registered, installed/enabled identity, path (up to 2,048 bytes, no control characters), printable title and Start capacity before atomically allocating the launch-link and tile records. Repeating the same app/path is idempotent. Launch links survive folder moves, resizing, phone reload and backup/restore. The canonical record is `PhoneData.app_links`; `TileTarget::AppLink(id)` references it. The legacy `Tile.app` enum is only a compatibility fallback for these tiles and must not be used to select their registration. New code resolves the link's app identity through the registry.

For a built-in registration, an empty path pins its normal app tile. A nonempty path requires both `.with_launch_path(parser)` and `.with_activation(handler)`. `AppRegistration::launch_payload(path)` validates the path, calls the parser, checks the JSON constraints and 64 KiB activation limit, and rejects an absent activation handler. `AppContext::pin` and `navigate` use this contract; the shell validates a persisted Start link again before navigating to the built-in and delivering its payload. The activation handler must revalidate the referenced record against current app data. Maps uses the canonical `place/<id>` route, rejects unsaved or deleted places, and removes their pins when a saved place is deleted. Extensions retain `Route::Extension { app, path }` navigation.

By default, extension tiles use the manifest icon/accent and saved label. `.with_tile(render)` supplies custom content:

```rust
fn render_tile(cx: phone_sdk::AppTileContext) -> phone_sdk::prelude::Element {
    use phone_sdk::prelude::*;
    let path = cx.path;
    rsx! { StackPanel { margin:12.0, spacing:8.0,
        {text("project", 24.0)}
        {muted(&path, 14.0)}
    }}
}
```

`AppTileContext` includes `app`, `size`, `width`, `height`, `path`, `now`, `live`, `animate` and `show_badge`. Respect `animate` before adding motion, honor `show_badge` for app-owned badges, and treat `now == 0` with `live == false` as a paused cadence. The shell supplies the label and the bounded tile container. Keep rendering side-effect free; use namespaced data or typed app state and the supplied cadence for live content. The system stops cadence updates when live tiles are disabled or obscured, and tile rendering does not itself create background execution. Weather's live tile is implemented through this same callback in the Weather app crate.

### Published tile cards

`AppContext::tile_updater() -> Result<TileUpdater, String>` creates a weak publisher for the current registered app and phone-document epoch. `tiles()` returns its currently pinned leaf tile IDs, including those inside folders. `publish(tile, notification)` and `clear(tile, tag)` recheck exact app/tile ownership on every call; a folder or another app's tile is rejected. Existing publishers become invalid after restore, app reset or close, disabling/removing the owning app, or host shutdown. They do not keep the view model or session alive.

```rust
use phone_sdk::{AppContext, TileBadge, TileNotification, TileTemplate};

fn publish_project_progress(cx: &AppContext) -> Result<(), String> {
    let updater = cx.tile_updater()?;
    let now = cx.vm.now();
    let mut card = TileNotification::new(
        "project.progress",
        TileTemplate::Progress {
            title: "Project plan".into(),
            body: "Review in progress".into(),
            percent: 65,
        },
        now,
    );
    card.expires_at = Some(now.saturating_add(3600));
    card.badge = Some(TileBadge::Count(3));
    for tile in updater.tiles()? {
        updater.publish(tile, card.clone())?;
    }
    Ok(())
}
```

`TileNotification` has `tag`, `starts_at`, `expires_at`, `template` and optional `badge` fields. Times are Unix seconds. Tags contain 1–32 ASCII letters, digits, dots, underscores or hyphens. A publication replaces the same tag, removes expired cards, then retains at most five cards per tile by dropping the oldest publication. Starts may be scheduled up to 30 days ahead; expiry must follow the start and cannot already have passed. `updater.clear(tile, Some("project.progress"))` removes one tag; `clear(tile, None)` removes all published cards on that owned tile.

| `TileTemplate` | Fields and limits |
| --- | --- |
| `Text` | `title`, `body`. |
| `Flip` | `title`, `body`, `back_title`, `back_body`; two sides. |
| `Photo` | Existing local library `photo` ID, `title`, `body`. |
| `Cycle` | `photos`: one to nine distinct existing local photo IDs; `title`. |
| `List` | `title`; `lines`: one to three nonempty lines, each at most 160 characters. |
| `Progress` | `title`, `body`; `percent`: 0–100. |

Titles are limited to 80 characters and bodies to 320. Photo identities cannot be arbitrary paths or URLs. `TileBadge` is `Count(u32)` or `Glyph(TileBadgeGlyph)`; counts above 99 display `99+` while accessibility retains the actual count. The shell honors saved `TileAppearance` preferences for the label, app/accent/custom-color/local-photo background, badge, live content and queue rotation.

Published cards are persistent phone data and participate in backup/restore. Eligible queued cards rotate every eight seconds when motion and the tile's queue setting permit it; otherwise the newest eligible card remains selected. Future and expired cards are excluded. With live content enabled, schedule and expiry boundaries still apply under reduced motion. One shell clock handles visible Start/folder deadlines; rotation and expiry never write storage and do not register an OS background task. An app remains responsible for obtaining and validating the content it publishes.

## Data activation

Use an app's route for normal navigation. For a structured activation, queue one JSON payload, then navigate to its destination. Delivery occurs after route lifecycle callbacks reset the destination UI:

```rust
let destination = cx.session.registry().by_id("phone.calendar")
    .ok_or("Calendar is unavailable")?.manifest.route("");
cx.session.queue_activation("phone.calendar", serde_json::to_value(occurrence)?)?;
cx.vm.navigate(destination);
```

The session keeps one pending activation, bounded to 64 KiB. Delivery uses `AppRegistry::activate`, which rejects unknown, disabled and inactive destinations and validates the JSON value. The destination owns payload decoding through `.with_activation`. Calendar reminders use this contract to open an exact occurrence without making the system or alarm service depend on the Calendar app crate. An activation is an in-process SDK message, not an implementation of Windows Phone URI-association or XAP activation compatibility.

## Host capabilities and surfaces

Use `AppContext::request` to request host services. It checks that the app remains installed/enabled and verifies the requested service family against the manifest's declared capabilities before forwarding to the existing host adapter. Declare only the families used by the app. The browser or native OS still owns its permissions, prompts and delivery outcome.

`AppManifest::new` starts with no host capabilities. The built-in registration constructor explicitly declares `Capability::All` for the trusted system apps' existing host commands. These declarations describe SDK service admission; linked Rust code shares the process and view model, so they are not a security sandbox.

```rust
let manifest = AppManifest::new("example.camera", "Camera tool", Icon::Camera)
    .capabilities(&[Capability::Camera]);
// Inside the registered app's event handler:
cx.request(phone_sdk::host::HostRequest::StartCamera)?;
```

### Typed file selection

`AppContext::choose_file(FilePickerOptions)` returns a `FileTask` future with `Result<Option<PickedFile>, String>`. Cancellation by the user returns `Ok(None)`; a selected file includes its display name, MIME type and byte vector. The manifest must declare `Capability::Files`. Options restrict extensions and a maximum byte count; the SDK validates host results again before completing the future.

Create the task synchronously inside the user event, before scheduling the async block, so browser file selection retains the original user activation:

```rust
let selection = cx.choose_file(phone_sdk::FilePickerOptions {
    extensions: vec![".txt".into(), ".md".into()],
    max_bytes: 256 * 1024,
});
let epoch = cx.vm.document_epoch();
let vm = cx.vm.clone();
drop(ferroui_base::threading::Dispatcher::current_dispatcher().spawn_local(async move {
    let result = selection.await;
    if vm.document_epoch() != epoch { return; }
    match result {
        Ok(Some(file)) => { /* Validate the content, then apply app-owned changes. */ }
        Ok(None) => {}
        Err(error) => vm.set_status(error),
    }
}));
```

The task is cancelled when its future is dropped, the app closes or resets, or the session ends. Stale completions after a phone restore cannot mutate the replacement document. OneNote's text/Markdown import is an end-to-end consumer of this API and rejects non-UTF-8/binary content before creating a note. The chooser is for one bounded file, not arbitrary filesystem access.

### Bounded HTTPS reads

`AppContext::get(url, max_bytes)` returns `phone_sdk::tasks::HttpTask`, a future yielding `Result<Vec<u8>, String>`. Declare `Capability::Network`. The SDK creates a request identifier, records the app/session and current `PhoneViewModel::document_epoch()`, then requests `HostRequest::HttpGet`. Hosts complete it through `complete_http`; they can use `is_http_task_pending` to avoid work or abort an obsolete request. Weather and Podcasts consume this contract without depending on browser JavaScript or native networking libraries.

```rust
let epoch = cx.vm.document_epoch();
let response = cx.get("https://example.org/feed.xml", 512 * 1024);
let completion = cx.clone();
drop(ferroui_base::threading::Dispatcher::current_dispatcher().spawn_local(async move {
    let result = response.await;
    if completion.vm.document_epoch() != epoch { return; }
    match result {
        Ok(bytes) => { /* Decode and validate the app's bounded data format. */ }
        Err(error) => completion.vm.set_status(error),
    }
}));
```

Admission permits public HTTPS domain names on port 443, without URL credentials, IP literals, local/reserved host suffixes or control characters. URLs are limited to 4,096 bytes and fragments are removed. Each request selects a response limit from one byte through 2 MiB; the SDK rechecks the returned byte count. At most eight HTTP task entries may be pending on a dispatcher, and each host request has a 15-second timeout. Responses contain bytes; they are not proof that JSON, XML, timestamps or application records are valid.

Requests use GET without application credentials, cookies, redirects or proxy configuration supplied by an app. Browser requests use CORS with omitted credentials, so a server must explicitly permit the browser origin. Native reads run on the system worker; the resolver rejects non-public addresses before connecting and pins the connection to its checked resolution. Both hosts report HTTP, size and transport failures instead of substituting example data. Use a feed's final HTTPS address when a server redirects.

Dropping the future cancels delivery. Closing/resetting/disabling an app, replacing the phone document, or destroying the session invalidates pending and completed-but-unconsumed results. Completion and future polling both revalidate app availability and document epoch; a late response cannot be applied to a restored phone even if its app ID is unchanged. The browser aborts obsolete fetches. A native blocking request already running can finish within its timeout, but its result is discarded after cancellation. Applications should additionally use an app-owned request generation when a newer search or refresh supersedes an older operation within the same document. This API supplies explicit bounded reads; it does not provide account synchronization, automatic polling, retries or OS background scheduling.

Normal navigation does not cancel a task. A completion may save its result while another screen is active, but should only navigate or replace a detail selection if its originating route and selection are still current. Podcasts applies this guard to feed subscription, refresh and file import.

Capabilities are an application contract for trusted code. `AppContext` exposes the existing view model, and statically linked Rust can access other public APIs; declarations are not a security sandbox. File selection, sharing, notification permission and location acquisition should remain explicit user actions. Do not request permissions just to populate a Settings page.

Camera and video app views place `host_surface(HostSurface::Camera)` or `host_surface(HostSurface::Video)` in their retained preview containers. A native host can install a control factory with `set_host_surface_factory`. An unavailable surface produces an empty element, preserving the normal view and browser overlay geometry. Host adapters own their native device/player lifecycle; the app owns layout and commands.

For the browser host, name the surrounding retained container `CameraViewport` or `MediaViewport` respectively, give it a background so the native inspection hit test identifies its bounds, and keep it inside the app's normal content area. The browser positions its permitted media element over that control. The built-in Camera and shared media views are concrete examples of this contract; using only `host_surface` without that container does not create a browser overlay. Host surfaces are foreground UI and do not grant background capture or playback scheduling.

Shared image helpers admit and cache application media for app lists, Photos, lock backgrounds and tiles. Use the existing host/SDK service rather than decoding arbitrary files independently in every app.

## Shared media queue and observations

`phone_sdk::media` owns the shell's transient library queue and observed playback position. Music, Video, Podcasts, browser Media Session keys and native system transports use this shared queue. Media bytes remain in host asset storage, while a playable `MediaTrack.source` identifies either a local `media:` asset or a validated HTTPS stream admitted by the host.

`media::start(vm, session, sources, selected, repeat, shuffle)` validates a nonempty queue of at most 10,000 distinct, existing library sources and requests actual host playback. It returns an error for an unavailable source, duplicate source or absent selection. The queue is a snapshot of the chosen collection; editing a playlist does not silently replace a running queue. A playback request does not set `Session::media_playing` optimistically: the host reports success, pause and failure.

`MediaQueue` keeps library order separately from shuffled order. Enabling shuffle preserves the current source; disabling it restores the original order without moving to a different source. `RepeatMode::One` repeats an ended item, while a manual Next still advances; `All` wraps at the queue boundaries and `Off` finishes at the last item. Previous at the first item restarts it, or wraps when repeat-all is selected. Removed library references are pruned before transport advancement. Music/Video playlists and Photos albums persist stable track/photo IDs in their owning app namespace, so asset-key remapping during backup restore does not break membership. Active queues are transient and never resume sources from a replaced phone document.

| SDK/host entry | Contract |
| --- | --- |
| `media::control(&Rc<PhoneViewModel>, &Rc<Session>, action)` | Handles `next`, `previous` and `ended`; returns `false` for controls owned by the host. Publishes completion/checkpoints before queue mutation. |
| `media::capabilities(vm, session)` | Returns `(can_next, can_previous)` for surviving library sources and the current repeat mode. |
| `PlaybackSession` | Typed session state with the queue plus finite, nonnegative observed position/duration signals in seconds. Unknown duration is zero. |
| `phone_ui::show_media(title, source, playing)` | Binds an actual host source and state. Source replacement or clearing flushes the previous source's last observation before resetting it. |
| `phone_ui::media_progress(position, duration)` | Records and publishes progress for the bound host source; it cannot create a new source binding. |
| `phone_ui::media_command(action)` | Routes browser/native transports through the same SDK control path. |

The SDK equivalents of the host state/progress bridges are `media::publish_state` and `media::publish_progress`. A host must publish a source before its progress, report its final position before `ended`, and keep its own asynchronous player-generation checks. Unrelated host callbacks must not be relabeled as the current source. The SDK keeps the host's last observation separately from queue UI resets, preserving the old source's checkpoint while a requested successor loads.

### Playback subscriptions

Register an opt-in handler with `.with_media_event(fn(AppContext, &PlaybackEvent))`; the types are in `phone_sdk::media`. `PlaybackEvent` has three variants carrying a `PlaybackSnapshot`:

| Event | Meaning |
| --- | --- |
| `Progress` | The active host's latest observed source, position and duration. Consumers should throttle persistent writes. |
| `Paused` | A checkpoint before a host pause, source replacement/clear, transport change or host suspension. It does not itself command the player to pause. |
| `Ended` | An actual host completion, delivered once before queue advancement and position reset. |

`PlaybackSnapshot` exposes `source`, `position`, `duration`, `document_epoch()` and `is_current(vm, session)`. Its private observation identity prevents an older sample from being delivered after a reentrant source or progress change. `AppRegistry::media_event` delivers independently of the active route, but only to installed built-ins or enabled extensions declaring `Capability::Media` or `Capability::All`. Before **every** subscriber it rechecks availability, the current library source, document epoch and observation identity. No document or event-state borrow is held across app callbacks. Restoring a document, deleting the source, disabling a subscriber or synchronously changing playback stops the corresponding stale delivery. Completion also checks whether a subscriber replaced the queue before issuing the next host request.

Podcasts is the reference consumer: it saves useful progress at a bounded cadence even while Start or another app is open, flushes exact positions on checkpoints, and marks matching episodes played only on `Ended`. Duplicate observations do not generate repeated document writes. Pending resume seeks wait for real host metadata so a temporary zero position does not overwrite the saved checkpoint.

Closing an app's recent card does not unregister its enabled, statically linked media observer; disabling the app stops delivery. Reset hooks still clear app-owned transient state, and a phone restore invalidates all old observations. These subscriptions run inside the existing live shell. They do not launch an app, keep a suspended browser alive, establish an OS background agent or grant media access to untrusted packages. Capability declarations remain a trusted-code contract, as with the rest of the SDK.

## Verification boundaries

The crate split preserves the existing native control IDs and app workflows so the rendered interaction suite can exercise the migrated implementation. Compile-time dependency checks establish the direction of reuse; Rust and JavaScript boundary tests establish selected state/host behavior; browser screenshots establish the rendered states they capture. None of those alone certifies original-device pixel parity, real OS permission dialogs, complete cloud-account services, dynamic third-party package loading or every physical platform.

See [host integration](host-integration.md), [interchange formats](pim-interchange.md), [architecture](architecture.md), and the revision-specific [verification record](parity.md) for implemented behavior and measured coverage.

## Pluggable platform hosts

App requests still go through the capability-checked `AppContext`. `Capability::Platform` admits typed `HostRequest::Platform` requests for observed device apps, OS settings and supported device services. Apps discover availability through `PhoneViewModel::platform_state`; they do not infer privilege from fullscreen presentation. Device apps is a standalone example of catalog discovery and stable opaque-ID pins.

Hosts compose `PhoneRuntime` with one `PlatformPlugin` and an explicit `ServiceRegistry`. Native application owners can add SDK registrations and replace service families through `NativeHost::compose` without forking app code or OS entry points. See the complete [embedding example and lifetime contract](platform-architecture.md#replaceable-services-and-application-composition). Native file handoff is a host-only plugin hook; it does not expose arbitrary filesystem paths through the app-facing PlatformRequest contract.
